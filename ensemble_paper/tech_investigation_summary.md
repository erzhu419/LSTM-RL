# 技术复盘：奖励异常、Q值分析与模型重训逻辑

本文总结了针对公交调度 RL 系统在调试过程中遇到的核心技术问题及其解决方案。

## 1. 异常脉冲 (Spike) 与平滑 (Smoothing) 处理

### 异常脉冲处理 (Spike Handling)
系统通过多重机制防止梯度爆炸和数值不稳定：
- **梯度裁剪 (Gradient Clipping)**：在 `update` 循环中使用 `torch.nn.utils.clip_grad_norm_`，将 Q 网络的梯度范数限制在 1.0 以内。这防止了由于单个异常巨大的 reward 导致的权重剧烈跳变。
- **Reward Scaling (奖励缩放)**：使用 `RewardScaling` 类，不仅对奖励进行标准差缩放，还结合了 `RunningMeanStd` 动态跟踪奖励分布。
- **状态归一化 (State Normalization)**：通过 `Normalization` 类对数值特征（车头间距、速度等）进行实时归一化，确保输入网络的数据保持在合理范围内。

### 平滑逻辑 (Smoothing)
- **目标网络软更新 (Polyak Averaging)**：Q 网络采用 `target_param * (1-tau) + param * tau` 的方式缓慢更新目标网络（`tau=1e-2` 或更小）。这在本质上是一种时间维度上的平滑，防止 Q 值目标发生剧烈偏移。
- **正则化项 (`weight_reg`)**：引入 L1/L2 权重惩罚项，限制网络复杂度的同时，也平滑了函数空间，避免出现极端的预测波谷。

## 2. “Zero Reward” 问题回顾

### 现象
在分析脚本 `analyze_q_accuracy.py` 中，最初计算出的 `Real Q` 始终为 0。

### 根源
1. **Horizon (展望时段) 过短**：分析脚本默认的 `horizon` 仅为 50 步。
2. **环境暖机期 (Warm-up Period)**：环境中前两个站点被设定为不产生奖励（用于建立车队间距）。公交车大约需要 200 步才能到达产生奖励的第三站。
3. **逻辑修复**：将 `horizon` 从 50 增加到 **500**。这样公交车有足够的时间运行到产生有效惩罚/奖励的路段，从而得到了真实的负值奖励。

## 3. Retraining 逻辑：为什么只有 Ensemble 需要重训？

### 核心原因：分布偏移 (Distribution Shift)
- **Ensemble 版模型“中毒”**：当前使用的 Ensemble 模型（如 `ensemble_10`）是在 **[Sticky Reward Bug]** 存在的期间训练的。
    - **训练环境奖励**：平均 -430,000（极大的负反馈地狱）。
    - **评估环境奖励**：平均 -50（修复 bug 后的“天堂”）。
- **SAC 处理可能的原因**：
    - `sac_v2_bus.py` 的模型可能是在干净的环境下重新训练过的，或者它的训练时间点避开了该 bug 最严重的时期。
    - **归一化参数丢失**：Ensemble 训练代码之前没有保存 `state_norm` 统计量。在推理时，模型面对干净环境的输入（Raw Data）和它在“地狱”中形成的权重产生了巨大的不匹配。

### 正则化项的影响
- Ensemble 版使用了更为敏感的 **LCB/UCB 采样** 和 **正则化聚合**（用于衡量不确定性）。当输入分布由于归一化缺失而发生一点偏移时，Ensemble 的方差项会迅速放大这种不一致性，导致 Q 值跳变到 +1800 这种离谱的数值。

---

## 总结
重训 Ensemble 模型是为了建立 **[干净环境 -> 干净统计量 -> 干净模型权重]** 的闭环，消除“历史残留隐患”对 Q 值准确性的干扰。
